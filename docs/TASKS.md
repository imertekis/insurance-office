# Σχέδιο Υλοποίησης (TASKS)

Το παρακάτω σχέδιο χωρίζει την υλοποίηση της εφαρμογής σε λογικά, διαδοχικά βήματα. Τα πιο επίφοβα (risky) κομμάτια, όπως η κανονικοποίηση κειμένου, το "έξυπνο" search και η εισαγωγή των Excel, τοποθετούνται πολύ νωρίς, ώστε τυχόν προβλήματα να εντοπιστούν πριν χτιστεί το UI και οι υπόλοιπες λειτουργίες πάνω τους.

Κάθε Task είναι σχεδιασμένο να υλοποιείται σε ένα session και να αφήνει την εφαρμογή λειτουργική, με τα tests της να περνούν επιτυχώς.

---

## Task 1: Project Skeleton & End-to-End Slice
**Στόχος:** Στήσιμο του περιβάλλοντος και δημιουργία του πρώτου λειτουργικού "end-to-end slice" της εφαρμογής (βάση, backend, api) με μόνο έναν πίνακα, ως απόδειξη ότι η υποδομή λειτουργεί.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `docker-compose.yml` (PostgreSQL)
*   `pom.xml` (Spring Boot Web, Data JPA, Flyway, PostgreSQL Driver, Testcontainers)
*   `application.yml` (DB connection, Flyway config)
*   `src/main/resources/db/migration/V1__init_customer.sql` (Δημιουργία πίνακα `customer` μόνο)
*   `Customer.java` (JPA Entity)
*   `CustomerRepository.java` (Spring Data Repo)
*   `CustomerController.java` (REST endpoint: `GET /api/customers`)
*   `CustomerControllerTest.java` (Integration test)
**Κριτήρια Αποδοχής:** Η εντολή `docker-compose up` ξεκινάει τη βάση. Το Spring Boot ξεκινάει χωρίς λάθη και τρέχει το Flyway migration. Μια κλήση στο `/api/customers` επιστρέφει JSON 200 OK. Το test περνάει επιτυχώς.

## Task 2: Search Normalization Foundation (High Risk)
**Στόχος:** Υλοποίηση της κανονικοποίησης κειμένου. Αυτό πρέπει να γίνει νωρίς, ώστε να υπάρχει ένα και μοναδικό σημείο αλήθειας (Single Source of Truth) τόσο για το Entity Lifecycle όσο και για το SearchService.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `V2__unaccent_wrapper.sql` (Extensions `unaccent`/`pg_trgm`, custom `IMMUTABLE` PostgreSQL συνάρτηση γύρω από την `unaccent`, στήλη `customer.search_normalized` ως `GENERATED ALWAYS AS (...) STORED` και GIN index πάνω της)
*   `TextNormalizationUtils.java` (Java utility class: αφαίρεση τόνων/κεφαλαία για το input αναζήτησης, κανονικοποίηση πινακίδας με αντιστοίχιση ελληνικών→λατινικών)
*   `TextNormalizationUtilsTest.java` (Unit tests)
*   `Customer.java` (Αντιστοίχιση του `search_normalized` ως read-only: `insertable = false, updatable = false`. **Όχι** `@PrePersist` για αυτό το πεδίο.)
*   `SearchNormalizationConsistencyTest.java` (Integration test με Testcontainers)
**Απόφαση:** Το `search_normalized` υπολογίζεται στη **βάση** (generated column), ώστε να γεμίζει και σε εγγραφές που παρακάμπτουν το JPA (import, χειροκίνητο SQL, migrations). Το `plate_normalized` μένει σε `@PrePersist`/`@PreUpdate` στο `Vehicle` (Task 3) μέσω του `TextNormalizationUtils`, γιατί η αντιστοίχιση ελληνικών→λατινικών είναι δύσχρηστη σε SQL.
**Κριτήρια Αποδοχής:** Το Flyway migration περνάει. Τα unit tests αποδεικνύουν ότι τα τονισμένα ελληνικά γίνονται άτονα, οι ελληνικοί χαρακτήρες πινακίδων (π.χ. 'Α', 'Β', 'Ε') γίνονται οι λατινικοί 'A', 'B', 'E', οι παύλες/κενά αφαιρούνται από τις πινακίδες και όλα μετατρέπονται σε κεφαλαία. Το `search_normalized` γεμίζει αυτόματα τόσο κατά την αποθήκευση Customer μέσω JPA όσο και με απευθείας `INSERT` σε SQL. Το consistency test επιβεβαιώνει ότι η Java κανονικοποίηση του input δίνει το ίδιο αποτέλεσμα με τη συνάρτηση της βάσης (τονισμένα, πεζά/κεφαλαία, τελικό σίγμα).

## Task 3: Πλήρες Σχήμα & MapStruct DTOs
**Στόχος:** Ολοκλήρωση του Data Model (χωρίς soft deletes) βάσει των προδιαγραφών και εισαγωγή των DTOs για την απομόνωση του domain model.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `V3__full_schema.sql` (Πίνακες `vehicle`, `policy`, `ownership`, `intermediary`, `app_user`, `audit_log` και GIN indexes)
*   Entities (`Vehicle.java`, `Policy.java` κλπ.)
*   Repositories για τα entities.
*   `pom.xml` (Προσθήκη MapStruct)
*   `*Dto.java` και `*Mapper.java` (MapStruct interfaces)
**Κριτήρια Αποδοχής:** Το Spring Data JPA ξεκινάει χωρίς errors για τις σχέσεις (OneToMany, ManyToMany). Το πεδίο `engine_cc` είναι nullable. Τα πεδία `tax_id` και `mobile` είναι nullable. Τα unique indexes υπάρχουν και δεν έχουν `WHERE deleted_at IS NULL`. Οι MapStruct mappers γίνονται generate στο compile-time επιτυχώς.

## Task 4: Excel Import Service (High Risk)
**Στόχος:** Ανάγνωση των παλιών Excel αρχείων και μεταφορά τους στη νέα βάση δεδομένων, ώστε να έχουμε ρεαλιστικά δεδομένα για το υπόλοιπο development.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `pom.xml` (Προσθήκη Apache POI)
*   `gr.insuranceoffice.importer.ExcelImporterService.java`
*   `ExcelImporterServiceTest.java`
**Κριτήρια Αποδοχής:** Η υπηρεσία διαβάζει ένα dummy Excel και το χαρτογραφεί στα entities. Μετατρέπει τα strings `«ΝΑΙ (Ν.Ο.Δ.)»` σε boolean. Αν το service τρέξει 2 φορές στο ίδιο αρχείο (idempotency), δεν δημιουργεί διπλότυπα αλλά κάνει update μέσω του natural key (`tax_id`, `vin`). Η εγγραφή "Αλεξίου Μαρία" σώζεται κανονικά παρόλο που λείπουν τα τηλέφωνα. 
**Σημείωση:** Ο importer είναι εργαλείο **εφάπαξ μετάπτωσης** από τα Excel, όχι λειτουργία καθημερινής χρήσης. Οι κίνδυνοι στο `docs/NOTES.md` («Import risks»: η επανεκτέλεση αντικαθιστά αλλαγές που έγιναν στην εφαρμογή, και αφαιρεί ιδιοκτησίες που λείπουν από το αρχείο) γίνονται πραγματικοί μόλις παραδοθούν τα Tasks 11a–11d, γιατί από εκεί και πέρα τα δεδομένα αλλάζουν μέσα από την εφαρμογή.

## Task 5: Έξυπνη Αναζήτηση (Smart Search)
**Στόχος:** Υλοποίηση της single search box λογικής με Type Detection μέσω Regex.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `SearchService.java`
*   `SearchServiceTest.java`
*   `SearchResultDto.java`
*   `SearchController.java`
**Κριτήρια Αποδοχής:** Το service δέχεται ένα input string. Αν κάνει match το VIN regex (`^[A-HJ-NPR-Z0-9]{17}$`), ψάχνει μόνο στο `VehicleRepository.findByVin()`. Αν είναι 9 ψηφία, στο ΑΦΜ. Αλλιώς, περνάει το input από το `TextNormalizationUtils`, εκτελεί fallback GIN query στους πίνακες `customer` και `vehicle`, συλλέγει τα αποτελέσματα και τα ομαδοποιεί. Τα tests επικυρώνουν σωστό routing του regex και απουσία N+1 queries.

## Task 7: Optimistic Locking & Advanced Validation
**Στόχος:** Εφαρμογή των επιχειρησιακών κανόνων και του concurrency control.
**Αρχεία (δημιουργία/τροποποίηση):**
*   Προσθήκη `@Version` πεδίου `version` σε Πελάτη, Όχημα, Συμβόλαιο.
*   `CustomerService.java` (Business validations)
*   `GlobalExceptionHandler.java` (Controller Advice)
**Κριτήρια Αποδοχής:** Μια ταυτόχρονη αλλαγή ρίχνει `OptimisticLockException` και το API επιστρέφει HTTP 409 Conflict. Η αποθήκευση Πελάτη **χωρίς κινητό** περνάει, ΕΚΤΟΣ αν ο πελάτης είναι "Κύριος Ιδιοκτήτης" (is_primary = true) σε ενεργό όχημα με τρέχον συμβόλαιο, οπότε και το service ρίχνει Business Exception. Απουσία ΑΦΜ δεν ρίχνει λάθος αλλά μπορεί να επιστρέψει προειδοποίηση.

## Task 11: Φόρμες Καταχώρησης (Δημιουργία & Επεξεργασία)

Το αρχικό Task 11 ήταν τέσσερις φόρμες σε ένα session. Σπάει σε πέντε
διαδοχικά Tasks (11a–11e), καθένα από τα οποία ολοκληρώνεται σε ένα session
και αφήνει την εφαρμογή λειτουργική με πράσινα tests. Η σειρά έχει σημασία:
η ιδιοκτησία χρειάζεται πελάτη και όχημα, το συμβόλαιο χρειάζεται όχημα, και
οι ρόλοι φυλάνε τις ενέργειες που προσθέτουν τα προηγούμενα.

Κοινά για όλες τις φόρμες (11a–11d):
*   Οι controllers δουλεύουν **μόνο με DTOs** και καλούν services· η επικύρωση ζει στα services και δεν επαναλαμβάνεται σε controller ή JavaScript.
*   Κάθε σφάλμα εμφανίζεται μέσα στη φόρμα, δίπλα στο πεδίο που αφορά (ή στην κορυφή, αν αφορά όλη την εγγραφή), και οι τιμές που πληκτρολογήθηκαν δεν χάνονται.
*   Σύγκρουση optimistic locking (Task 7) εμφανίζει μήνυμα στη φόρμα και δεν αντικαθιστά σιωπηλά την αλλαγή του άλλου χρήστη· το `version` ταξιδεύει ως κρυφό πεδίο.
*   Οι φόρμες είναι POST με CSRF token (Task 10) και κάθε αποθήκευση καταγράφεται στο `audit_log` με τον συνδεδεμένο χρήστη (Tasks 6, 10).
*   Ελληνικές ετικέτες, τιμές enum όπως στο `DATA_MODEL.md`, ημερομηνίες `dd/MM/yyyy`, ποσά με ελληνική μορφή.

### Task 11c: Φόρμα Ιδιοκτησίας
**Στόχος:** Σύνδεση πελατών με όχημα και ποσοστά, με τον κανόνα του `OwnershipService` (Task 3/4) να επιβάλλεται από το UI.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `templates/ownership-form.html`
*   `OwnershipController.java`
*   `OwnershipService.java` (φόρτωση των τρεχόντων ιδιοκτητών ενός οχήματος και αποθήκευσή τους μαζί, σε ένα transaction)
*   Integration tests
**Κριτήρια Αποδοχής:** Η φόρμα επεξεργάζεται **μαζί όλους τους τρέχοντες ιδιοκτήτες** ενός οχήματος, αφού μία-μία γραμμή δεν μπορεί να περάσει τον έλεγχο. Ο υπάλληλος προσθέτει και αφαιρεί γραμμές, επιλέγει πελάτη με αναζήτηση (ΑΦΜ ή όνομα· αν δεν υπάρχει, δημιουργείται πρώτα με τη φόρμα του Task 11a) και ορίζει ποσοστά. Το άθροισμα των ποσοστών = 100 και ακριβώς ένας κύριος ιδιοκτήτης, αλλιώς η αποθήκευση απορρίπτεται με μήνυμα στην κορυφή της φόρμας. Δεν επιτρέπεται να γίνει κύριος ιδιοκτήτης οχήματος με τρέχον συμβόλαιο πελάτης χωρίς κινητό (DECISIONS §1, `docs/NOTES.md` «Mobile rule from the other side»).
**Απόφαση:** Όταν αφαιρείται ιδιοκτήτης, η γραμμή **κλείνει με `to_date`**, δεν διαγράφεται. Η μεταβίβαση είναι γεγονός με ημερομηνία, και η καρτέλα οχήματος (Task 9) ήδη δείχνει τους πρώην ιδιοκτήτες ξεθωριασμένους — η διαγραφή θα έκανε αυτή τη λειτουργία νεκρό κώδικα. Άρα η φόρμα δεν αφαιρεί ποτέ γραμμές από τη βάση και **δεν χρειάζεται `orphanRemoval`** στο `Vehicle.ownerships` (`docs/NOTES.md`, Finding 2).

### Task 11d: Φόρμα Συμβολαίου
**Στόχος:** Δημιουργία και επεξεργασία Συμβολαίου, με τους κανόνες του συμβολαίου στο `PolicyService`. Είναι η φόρμα που θα ξαναχρησιμοποιήσει το Task 12.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `templates/policy-form.html`
*   `PolicyController.java`
*   `PolicyService.java` (`create`/`update` + επικύρωση)
*   Integration tests
**Κριτήρια Αποδοχής:** Ο υπάλληλος δημιουργεί και επεξεργάζεται συμβόλαιο από την καρτέλα οχήματος. Επικύρωση στο `PolicyService`:
*   μοναδικός αριθμός συμβολαίου
*   λήξη > έναρξη
*   συμβόλαια του ίδιου οχήματος που δεν επικαλύπτονται χρονικά· **η κοινή ημέρα ορίου δεν είναι επικάλυψη** (βλ. Απόφαση παρακάτω)
*   ασφάλιστρο αριθμητικό με 2 δεκαδικά (όχι κείμενο «180,00 €»)· η ελληνική υποδιαστολή γίνεται δεκτή στην είσοδο
*   τύπος επασφαλίστρου μόνο όταν υπάρχει επασφάλιστρο, με τις τιμές `ΝΕΟΣ_ΟΔΗΓΟΣ` / `ΗΛΙΚΙΑΣ` / `ΑΛΛΟ`

### Task 16f-2: Μία υποβολή ανά φόρμα, προειδοποίηση για αλλαγές που δεν σώθηκαν
**Στόχος:** Το δεύτερο μέρος του 16f, προστασία των φορμών: (1) ένα διπλό κλικ δεν στέλνει τη φόρμα δύο φορές· (2) ο browser προειδοποιεί πριν φύγει ο χρήστης με αλλαγές που δεν σώθηκαν, και στη φόρμα ιδιοκτητών από την πρώτη απόδοση όταν οι γραμμές της δεν έχουν σωθεί.
**Εξαιρέσεις στον κοινό κανόνα του Task 16** («καμία αλλαγή στο πώς δουλεύουν οι φόρμες»), με το όνομά τους:
1.  το κουμπί υποβολής απενεργοποιείται μετά το πρώτο κλικ (μέρος 1)· συμπεριφορά του browser
2.  ο browser προειδοποιεί πριν φύγει ο χρήστης με αλλαγές που δεν σώθηκαν (μέρος 2)· συμπεριφορά του browser
3.  η φόρμα ιδιοκτητών σημειώνεται στον server όταν οι γραμμές της διαφέρουν από τους αποθηκευμένους ιδιοκτήτες, ώστε η προειδοποίηση να ισχύει από την πρώτη απόδοση (μέρος 2, «Απόφαση (φόρμα ιδιοκτητών)»). Είναι μόνο ένδειξη προς τη σελίδα: ό,τι σώζεται και πώς ελέγχεται δεν αλλάζει.

Πέρα από αυτά, στον server δεν αλλάζει τίποτα: routes, validation, δικαιώματα και αναζήτηση μένουν ίδια.

#### 1. Μία υποβολή ανά φόρμα
*   **Γιατί:** Ένα διπλό κλικ στο «Αποθήκευση» στέλνει δύο αιτήματα. Σε νέο πελάτη χωρίς ΑΦΜ μπορεί να γίνουν δύο εγγραφές (χωρίς ΑΦΜ δεν υπάρχει unique έλεγχος). Σε επεξεργασία, το δεύτερο αίτημα βλέπει το μήνυμα σύγκρουσης του optimistic locking. Δεν μετρήθηκε· είναι ο λόγος του κριτηρίου.
*   **Αρχείο:** `static/js/app.js` του 16e, ένας κοινός χειρισμός για κάθε φόρμα `method="post"`, όχι script ανά σελίδα. Οι φόρμες σήμερα:
    *   πελάτη, οχήματος, συμβολαίου, ιδιοκτητών
    *   επιβεβαίωση διαγραφής
    *   σύνδεση, αποσύνδεση
*   Οι φόρμες `method="get"` εξαιρούνται, γιατί η επανάληψή τους δεν αλλάζει δεδομένα: η αναζήτηση του header και τα φίλτρα της αρχικής και των συμβολαίων. Το φίλτρο της αρχικής υποβάλλεται μόνο του με κάθε αλλαγή.
**Προσοχή (όνομα και τιμή του κουμπιού):**
*   Ένα **απενεργοποιημένο** κουμπί δεν στέλνεται με τη φόρμα, ούτε το ίδιο το κουμπί που πατήθηκε (HTML: τα disabled controls μένουν έξω από τα δεδομένα της φόρμας). Αν απενεργοποιηθεί στο `click` ή στο `submit`, χάνεται το όνομα και η τιμή του.
*   Η φόρμα ιδιοκτητών στηρίζεται σε αυτά: `action=save` / `search` / `refresh`, `remove=<id>`, `add=<id>`.
*   Γι' αυτό η πρώτη υποβολή περνά κανονικά και κάθε επόμενη υποβολή της ίδιας φόρμας ακυρώνεται (`preventDefault`). Τα κουμπιά δείχνουν απενεργοποιημένα **αφού** φτιαχτεί το αίτημα, π.χ. σε `setTimeout(…, 0)`, ή με κλάση και `aria-disabled` αντί για `disabled`.
**Προσοχή (πίσω):** Με «Πίσω» ο browser μπορεί να επαναφέρει τη σελίδα από το bfcache με τα κουμπιά απενεργοποιημένα. Ενεργοποιούνται ξανά στο `pageshow` με `event.persisted`.
**Κριτήρια Αποδοχής:**
*   Διπλό κλικ στο «Αποθήκευση» νέου πελάτη δημιουργεί **μία** εγγραφή.
*   Μετά το πρώτο κλικ τα κουμπιά υποβολής της φόρμας φαίνονται απενεργοποιημένα.
*   Κάθε κουμπί της φόρμας ιδιοκτητών (Αναζήτηση, Προσθήκη, Αφαίρεση, Αποθήκευση, και το Enter που πατά το κρυφό «Ανανέωση») κάνει ό,τι και πριν. Τα υπάρχοντα integration tests το ελέγχουν στον server· εδώ ελέγχεται και στον browser.
*   Μετά από λάθη validation η σελίδα ξαναφορτώνεται με ενεργά κουμπιά. Το ίδιο μετά από «Πίσω».

#### 2. Προειδοποίηση για αλλαγές που δεν σώθηκαν
*   **Αρχείο:** `static/js/app.js`. Ισχύει για τις φόρμες πελάτη, οχήματος, συμβολαίου και ιδιοκτητών. Όχι για τη σύνδεση, την επιβεβαίωση διαγραφής ή την αναζήτηση.
*   **Μηχανισμός:** Όταν φορτώνει η σελίδα κρατιέται ένα στιγμιότυπο των πεδίων με όνομα (`FormData`, χωρίς το `_csrf`). Παίρνεται **μετά** την αρχικοποίηση του flatpickr (16a), του οποίου το ορατό πεδίο δεν έχει όνομα· μετρά το αρχικό πεδίο ISO. Στο `beforeunload` συγκρίνεται με την τρέχουσα κατάσταση· αν διαφέρει, ζητείται προειδοποίηση.
*   **Δεν** προειδοποιεί όταν υποβάλλεται η φόρμα, με οποιοδήποτε κουμπί της. Στη φόρμα ιδιοκτητών αυτό περιλαμβάνει τα Αναζήτηση / Προσθήκη / Αφαίρεση, που ξαναφορτώνουν τη σελίδα.
*   **Δεν** προειδοποιεί μετά από επανεμφάνιση με λάθη validation, αν οι τιμές δεν άλλαξαν ξανά: το στιγμιότυπο είναι οι τιμές όπως ξαναφορτώθηκαν. Αυτές δεν έχουν σωθεί, αλλά ο χρήστης τις βλέπει μαζί με τα λάθη. Είναι η απόφαση για αυτή την περίπτωση, εκτός από τη φόρμα ιδιοκτητών (βλ. «Απόφαση (φόρμα ιδιοκτητών)»).
*   Αλλαγή και επαναφορά στην αρχική τιμή δεν προειδοποιεί.
*   Ο browser δείχνει δικό του κείμενο· δικό μας μήνυμα δεν γίνεται. Ο Chrome το δείχνει μόνο αν ο χρήστης έχει αλληλεπιδράσει με τη σελίδα (η πληκτρολόγηση μετρά).
**Απόφαση (φόρμα ιδιοκτητών):** Οι γραμμές που προστίθενται ή αφαιρούνται με τα κουμπιά της φόρμας δεν έχουν σωθεί ακόμα, αλλά η σελίδα ξαναφορτώνεται μαζί τους. Με μόνο τον κανόνα του στιγμιότυπου, αυτή η κατάσταση θα ήταν το στιγμιότυπο, και ο χρήστης που φεύγει μετά από «Προσθήκη» δεν θα προειδοποιούνταν. Γι' αυτό η σελίδα μαθαίνει από τον server αν οι γραμμές της διαφέρουν από τους αποθηκευμένους ιδιοκτήτες, και τότε η προειδοποίηση ισχύει **από την πρώτη απόδοση**, πριν αλλάξει οτιδήποτε στον browser. Είναι η τρίτη εξαίρεση στον κοινό κανόνα του Task 16 (βλ. την αρχή του 16f-2).
*   **Αρχεία:**
    *   `OwnershipService.java` και `OwnersFormDto.java`: το `ownersForm(vehicleId, submission)`, που ήδη φορτώνει τους αποθηκευμένους ιδιοκτήτες για να φτιάξει τη φόρμα, λέει και αν διαφέρουν οι γραμμές (π.χ. πεδίο `unsaved` στο `OwnersFormDto`). Η σύγκριση μένει στο service, γιατί ο controller δεν διαβάζει repositories (CLAUDE.md).
    *   `OwnershipController.java`: περνά την ένδειξη στη σελίδα όπως κάθε άλλο πεδίο της φόρμας, χωρίς δική του λογική.
    *   `templates/ownership-form.html`: `data-unsaved="true"` στη φόρμα όταν ισχύει.
    *   `static/js/app.js`: μια φόρμα με `data-unsaved="true"` προειδοποιεί χωρίς να συγκρίνει στιγμιότυπο. Οι άλλοι κανόνες του μέρους 2 μένουν: καμία ερώτηση όταν υποβάλλεται.
*   **Τι σημαίνει «διαφέρουν»:** άλλο σύνολο πελατών, ή άλλο ποσοστό ή άλλος κύριος ιδιοκτήτης σε κάποιον από αυτούς.
    *   Τα ποσοστά συγκρίνονται ως αριθμοί: «50», «50,00» και «50.0» είναι το ίδιο.

## Task 18: Παραβίαση μοναδικότητας χωρίς σφάλμα 500
**Στόχος:** Όταν ένας unique περιορισμός της βάσης απορρίπτει μια εγγραφή, ο χρήστης βλέπει ελληνικό μήνυμα δίπλα στο πεδίο της φόρμας ή στη γραμμή της εισαγωγής, όχι σελίδα 500 ή το κείμενο της PostgreSQL.
*   **Φόρμες (REVIEW-06, finding 1):** Τα services ελέγχουν τη μοναδικότητα με ένα SELECT **πριν** το INSERT/UPDATE. Αν δύο υπάλληλοι σώσουν ταυτόχρονα το ίδιο ΑΦΜ, περνούν και οι δύο τον έλεγχο και ο δεύτερος παίρνει 500: κανένας handler δεν πιάνει το `DataIntegrityViolationException` (ο `ViewExceptionHandler` χειρίζεται μόνο το `NotFoundException`).
*   **Εισαγωγή:** Η εισαγωγή ήδη πιάνει το σφάλμα και σταματά, αλλά το μήνυμα γραμμής είναι το κείμενο της PostgreSQL («duplicate key value violates unique constraint …»).
*   **Χωρισμός από το Task 17:** Το Task 17 προσθέτει στην εισαγωγή *έλεγχο* διπλής πινακίδας πριν την εγγραφή. Το Task 18 καλύπτει ό,τι φτάνει παρ' όλα αυτά στη βάση: ταυτόχρονες αποθηκεύσεις, και indexes χωρίς προηγούμενο έλεγχο.
*   **Ένας νέος έλεγχος, της ιδιοκτησίας:** Για τους άλλους indexes το Task 18 δεν προσθέτει έλεγχο πριν την εγγραφή· ό,τι φτάνει στη βάση μεταφράζεται σε μήνυμα. Η ιδιοκτησία της ίδιας ημέρας όμως δεν είναι αγώνας δύο υπαλλήλων: είναι ένας υπάλληλος που διορθώνει λάθος του. **Ο έλεγχος της ιδιοκτησίας.** Στο `saveOwners`, μαζί με τους άλλους ελέγχους και πριν από κάθε εγγραφή:

**Πώς αναγνωρίζεται ο index: από το όνομα, ποτέ από το κείμενο.**
*   Νέο `service/UniqueConstraint.java`: ένα enum με μία τιμή ανά index της λίστας (εκτός από το `idx_app_user_username`). Κάθε τιμή κρατά το όνομα του index, το πεδίο του DTO (null για τον διαμεσολαβητή) και το μήνυμα της φόρμας.
*   `UniqueConstraint.violatedBy(DataIntegrityViolationException)` επιστρέφει `Optional<UniqueConstraint>`. Ψάχνει στην αλυσίδα των αιτιών ένα `org.postgresql.util.PSQLException` με SQLState `23505` (unique_violation) και διαβάζει το `getServerErrorMessage().getConstraint()`. Αυτό είναι το πεδίο `n` του πρωτοκόλλου της PostgreSQL, που για unique index φέρει το όνομα του index (επαληθεύτηκε στην αναπαραγωγή). Άλλο SQLState, άλλο όνομα, ή καμία `PSQLException` δίνει κενό.
*   **Όχι** το `ConstraintViolationException.getConstraintName()` του Hibernate: δίνει το ίδιο όνομα, αλλά το βγάζει από το κείμενο του μηνύματος (`TemplatedViolatedConstraintNameExtractor` στο `PostgreSQLDialect`), που αλλάζει με το `lc_messages` του server.
*   **Η `PSQLException` εμφανίζεται μόνο μέσα στο `UniqueConstraint`.** Controllers, `FormErrors` και εισαγωγή βλέπουν μόνο το enum: `violatedBy(…)`, `field()`, `message()`. Αν αλλάξει ο τρόπος που διαβάζεται το όνομα, αλλάζει ένα αρχείο. (Το `UniqueConstraintTest` τη χρησιμοποιεί για να φτιάξει την είσοδό του.)
*   **Ένας βοηθός για τις φόρμες:** `FormErrors.show(DataIntegrityViolationException, Model)`, δίπλα στο υπάρχον `FormErrors.show(BusinessException, Model)`. Καλεί το `UniqueConstraint.violatedBy(e)` και περνά τη μία `Violation(field(), message())` από τον ίδιο δρόμο με τα λάθη του service: μήνυμα δίπλα στο πεδίο. Οι επτά `catch` των controllers καλούν μόνο αυτόν, οπότε η αντιστοίχιση «παραβίαση → λάθος πεδίου» γράφεται μία φορά. Αν ο index δεν είναι στη λίστα ή δεν έχει πεδίο φόρμας (ο διαμεσολαβητής), ο βοηθός ξαναρίχνει την ίδια εξαίρεση: ένας άγνωστος περιορισμός (π.χ. foreign key, check) είναι bug και μένει 500, όπως σήμερα.
*   Ο έλεγχος πριν την εγγραφή στα `CustomerService`, `VehicleService` και `PolicyService` παίρνει πεδίο και μήνυμα από το ίδιο enum. Έτσι ο υπάλληλος βλέπει ένα κείμενο για έναν κανόνα, είτε τον έπιασε ο έλεγχος είτε η βάση. Τα μηνύματα της λίστας είναι τα σημερινά των ελέγχων, εκτός από το νέο της ιδιοκτησίας.
*   `pom.xml`: ο driver `org.postgresql:postgresql` από `runtime` σε `compile` scope, γιατί ο κώδικας πλέον αναφέρει την `PSQLException`.

**Όριο συναλλαγής και πού πιάνεται η εξαίρεση.** Αν η εξαίρεση πιαστεί μέσα σε μέθοδο `@Transactional` και η μέθοδος τελειώσει κανονικά, η συναλλαγή έχει ήδη σημειωθεί rollback-only (η εξαίρεση πέρασε από το `@Transactional` του `SimpleJpaRepository`) και το commit αποτυγχάνει με `UnexpectedRollbackException`. Επιπλέον η PostgreSQL απορρίπτει κάθε επόμενη εντολή της ίδιας συναλλαγής (SQLState `25P02`). Ανά διαδρομή:
*   **Φόρμες πελάτη, οχήματος, συμβολαίου:** Όριο είναι οι μέθοδοι `create`/`update` των `CustomerService`, `VehicleService`, `PolicyService` (η ανανέωση περνά από το `PolicyService.create`). Κάνουν `saveAndFlush`/`flush` μέσα τους, οπότε η παραβίαση εμφανίζεται μέσα στη μέθοδο, βγαίνει από το proxy, και η συναλλαγή γίνεται rollback. Ο controller παίρνει `DataIntegrityViolationException` (επαληθεύτηκε).
*   **Φόρμα ιδιοκτητών:** Όριο είναι το `OwnershipService.saveOwners`. Η νέα γραμμή γράφεται στο `save` (IDENTITY, INSERT αμέσως), ή το αργότερο στο commit του proxy. Και στις δύο περιπτώσεις ο controller παίρνει `DataIntegrityViolationException` μετά το rollback (επαληθεύτηκε).
*   **Εκεί πιάνεται, στον controller, έξω από τη συναλλαγή:** `catch (DataIntegrityViolationException e)` δίπλα στο υπάρχον `catch (BusinessException e)`, σε κάθε POST που σώζει:
    *   `CustomerController.create`, `update`
    *   `VehicleController.create`, `update`
    *   `PolicyController.create` (νέο και ανανέωση), `update`
    *   `OwnershipController.submit` (κλάδος `save`)

    Κάθε `catch` καλεί το `FormErrors.show(e, model)` και ξαναδείχνει τη φόρμα όπως μετά από `BusinessException`. Το ποιος index είναι ποιο πεδίο ζει στο enum (service package), και η μετατροπή σε λάθος φόρμας στο `FormErrors`. Ο controller μόνο πιάνει και παραδίδει.

## Task 19: Ξαναπροσθήκη ιδιοκτήτη που αφαιρέθηκε με την ίδια ημερομηνία μεταβίβασης
**Πρέπει να γίνει πριν η εφαρμογή μπει σε χρήση στο γραφείο:** αλλιώς κάθε τέτοια διόρθωση θέλει ΔΙΑΧΕΙΡΙΣΤΗ ή αφήνει ψεύτικη μεταβίβαση στο ιστορικό των πραγματικών οχημάτων.
**Στόχος:** Ο υπάλληλος αφαιρεί κατά λάθος έναν ιδιοκτήτη, σώζει, και τον ξαναπροσθέτει με την ίδια ημερομηνία μεταβίβασης. Η αποθήκευση **ξανανοίγει** την κλειστή γραμμή του, αντί να γράψει νέα, και η διόρθωση πετυχαίνει χωρίς ίχνος στην καρτέλα.
**Σήμερα** (μετά το Task 18):
*   **Ο ιδιοκτήτης είχε μπει την ίδια ημερομηνία** (έναρξη = λήξη = ημερομηνία μεταβίβασης): το Task 18 απορρίπτει την αποθήκευση με το πρώτο μήνυμα του ελέγχου της ιδιοκτησίας. Η διόρθωση θέλει ΔΙΑΧΕΙΡΙΣΤΗ να διαγράψει την κλειστή γραμμή.
*   **Ο ιδιοκτήτης είχε μπει νωρίτερα** (έναρξη παλαιότερη, ή κενή από την εισαγωγή): κανένα λάθος, αλλά γράφεται δεύτερη γραμμή, δηλαδή μια μεταβίβαση που δεν έγινε.
    *   **Αναπαράχθηκε** με προσωρινό test (Testcontainers, μέσα από τη φόρμα, και μετά αφαιρέθηκε), και στις δύο μορφές: ιδιοκτήτης από την εισαγωγή (κενή έναρξη) και ιδιοκτήτης με έναρξη πριν 100 ημέρες. Όχημα με δύο ιδιοκτήτες 50/50· αποθήκευση μόνο του πρώτου με 100% και ημερομηνία σήμερα· αποθήκευση και των δύο 50/50 με ημερομηνία σήμερα.
    *   Και οι δύο αποθηκεύσεις πετυχαίνουν (redirect στην καρτέλα).
    *   Ο δεύτερος ιδιοκτήτης έχει μετά **δύο** γραμμές: την κλειστή (έναρξη όπως ήταν, λήξη σήμερα) και μια νέα (έναρξη σήμερα, τρέχουσα).
    *   Η καρτέλα οχήματος τον δείχνει δύο φορές: τρέχοντα από σήμερα («σήμερα / —») και «Πρώην» έως σήμερα («— / σήμερα» για τον εισαγμένο).
    *   Το `audit_log` γράφει `UPDATE` (λήξη κενή → σήμερα) στην παλιά γραμμή και `CREATE` της νέας.
**Κανόνας:** Πελάτης που **μπαίνει** (δεν είναι τρέχων ιδιοκτήτης) με ημερομηνία μεταβίβασης ίση με τη **λήξη** μιας κλειστής ιδιοκτησίας του στο ίδιο όχημα δεν παίρνει νέα γραμμή. Η κλειστή γραμμή ξανανοίγει:
*   η λήξη γίνεται κενή
*   ποσοστό και κύριος ιδιοκτήτης από τη φόρμα
*   η έναρξη μένει όπως ήταν, κενή ή όχι
*   Ο κανόνας κοιτά την ημερομηνία, όχι το «σήμερα»: η φόρμα προτείνει τη σημερινή, που είναι και η λήξη μιας αφαίρεσης που έγινε σήμερα. Μια αναδρομική ημερομηνία ίση με παλιότερη λήξη σημαίνει επίσης «δεν έφυγε ποτέ».
*   Αν ο πελάτης έχει περισσότερες κλειστές γραμμές που λήγουν εκείνη την ημέρα (μόνο σε δεδομένα πριν το Task 19), ξανανοίγει αυτή με την πιο πρόσφατη έναρξη· η κενή έναρξη μετρά ως η παλαιότερη, και σε ισοπαλία το μεγαλύτερο `id`.
*   Κλειστή ιδιοκτησία με άλλη λήξη δεν ξανανοίγει: ο πελάτης μπαίνει με νέα γραμμή όπως σήμερα, ή παίρνει το δεύτερο μήνυμα του Task 18 αν η έναρξή της είναι η ημερομηνία μεταβίβασης.
*   Το ξανάνοιγμα αλλάζει μόνο τη λήξη, οπότε ο unique index (vehicle, customer, start) δεν παραβιάζεται.
**Σχέση με τον έλεγχο του Task 18:**
*   Η περίπτωση του πρώτου μηνύματος (έναρξη = λήξη = ημερομηνία μεταβίβασης) είναι πλέον ξανάνοιγμα, οπότε το πρώτο μήνυμα φεύγει από το `checkRejoining`.
*   Οι πελάτες που ξανανοίγουν εξαιρούνται από τον έλεγχο, αφού δεν γράφουν νέα γραμμή.
*   Το δεύτερο μήνυμα (παλαιότερη περίοδος με έναρξη την ημερομηνία μεταβίβασης και λήξη μετά από αυτήν) μένει όπως είναι, όπως και το μήνυμα του index για την ταυτόχρονη αποθήκευση.
**Τι δεν αλλάζει:**
*   Ο κανόνας του 100%, ο ένας κύριος ιδιοκτήτης, ο κανόνας του κινητού (DECISIONS §1), η υποχρεωτική ημερομηνία μεταβίβασης και ο έλεγχος του version: όλα ελέγχουν τη φόρμα όπως υποβλήθηκε, πριν από κάθε εγγραφή.

**Στόχος:** (1) Η φόρμα ιδιοκτητών συμπληρώνει μόνη της τα ποσοστά στις απλές περιπτώσεις και δείχνει το σύνολο στις υπόλοιπες, ώστε ο υπάλληλος να μη λογαριάζει το 100%. #### 1. Ποσοστά στη φόρμα ιδιοκτητών
*   **Ένας ιδιοκτήτης:** το ποσοστό του γίνεται 100.
    *   Η «Αφαίρεση» και η «Προσθήκη» ξαναφορτώνουν τη σελίδα από τον server, οπότε ο κανόνας εφαρμόζεται όταν φορτώνει η σελίδα: **μία** γραμμή, φόρμα σημειωμένη `data-unsaved="true"` (16f-2), και **κανένα** μήνυμα λάθους στη σελίδα. Έτσι καλύπτει την αφαίρεση των άλλων και τον πρώτο ιδιοκτήτη οχήματος χωρίς ιδιοκτήτες.
    *   Δεν αλλάζει ποτέ μόνο του ό,τι είναι σωσμένο (πρώτο άνοιγμα, `data-unsaved` απών), ούτε ό,τι απέρριψε ο server: μετά από απορριφθείσα «Αποθήκευση» ο υπάλληλος βλέπει την τιμή του δίπλα στο λάθος της.
*   **Δύο ιδιοκτήτες:** η πληκτρολόγηση στο ένα ποσοστό κάνει το άλλο 100 μείον αυτό, και από τις δύο πλευρές: μετράει όποιο πληκτρολογήθηκε τελευταίο.
    *   Μόνο όταν η τιμή διαβάζεται, είναι πάνω από 0 και κάτω από 100 και έχει το πολύ δύο δεκαδικά. Αλλιώς το άλλο πεδίο δεν αλλάζει.
    *   Η πράξη γίνεται σε εκατοστά (ακέραιους), ώστε το 100 − 33,33 να βγαίνει 66,67 και όχι 66,66999…
    *   Το αποτέλεσμα γράφεται με υποδιαστολή και χωρίς περιττά μηδενικά: «70», «49,5», «66,67».
    *   Στη φόρτωση δεν αλλάζει τίποτα: μετά από «Προσθήκη» δεύτερου ιδιοκτήτη ο πρώτος μένει 100 και ο νέος κενός, μέχρι να πληκτρολογηθεί κάτι.
*   **Τρεις ή περισσότεροι:** καμία αυτόματη αλλαγή. Κάτω από τον πίνακα, μια γραμμή που ενημερώνεται με κάθε πληκτρολόγηση:
    *   «Σύνολο: 90% · λείπουν 10%», «Σύνολο: 110% · περισσεύουν 10%», «Σύνολο: 100%»
    *   Κενό πεδίο μετράει 0. Αν κάποιο ποσοστό δεν διαβάζεται: «Σύνολο: — · ένα ποσοστό δεν είναι αριθμός».
    *   `aria-live="polite"`, ώστε να το ακούει και ο αναγνώστης οθόνης.

**Προσοχή (16f-2):**
*   **Στιγμιότυπο:** Η συμπλήρωση του ενός ιδιοκτήτη στη φόρτωση γίνεται **πριν** το στιγμιότυπο της προειδοποίησης (`remember()` στο `app.js`): ο listener της καταχωρείται πριν από εκείνον του `remember`, οπότε η τιμή 100 είναι μέρος της αρχικής κατάστασης. Η σελίδα είναι έτσι κι αλλιώς `data-unsaved`, άρα η έξοδος ρωτά.

## Task 28: Όριο μήκους σε κάθε πεδίο κειμένου
**Στόχος:** Κάθε πεδίο κειμένου κάθε φόρμας, και κάθε κελί κειμένου της εισαγωγής, ελέγχεται για το μήκος της στήλης του πριν φτάσει στη βάση: στη φόρμα μήνυμα δίπλα στο πεδίο αντί για σελίδα σφάλματος, στην εισαγωγή όλα τα μεγάλα κελιά σε μία αναφορά. **Πριν από την πραγματική εισαγωγή**, όπως το Task 23 (Task 23, απόφαση 10)· ανεξάρτητο από αυτό, σε όποια σειρά.
**Τι ισχύει σήμερα:**
*   Μόνο ο αριθμός συμβολαίου έχει όριο μήκους (30, `PolicyService`). Το ΑΦΜ, το κινητό, το σταθερό, οι Τ.Κ. και το VIN το έχουν έμμεσα, από τη μορφή τους. Τα υπόλοιπα όχι, ούτε το email (έλεγχος μορφής χωρίς όριο, στήλη 255) ούτε η πινακίδα (στήλη 10).
*   Μια τιμή μεγαλύτερη από τη στήλη την απορρίπτει η PostgreSQL· το `FormErrors` ξαναπετά ό,τι δεν είναι unique index, οπότε ο υπάλληλος βλέπει σελίδα σφάλματος (από τον κώδικα, δεν αναπαράχθηκε).
*   Η εισαγωγή είναι όλα ή τίποτα (μία συναλλαγή) και μαζεύει όσα λάθη βρίσκει η ίδια. Μια γραμμή που την απορρίπτει η βάση όμως τη σταματά αμέσως, γιατί η PostgreSQL δεν δέχεται άλλη εντολή στη συναλλαγή: ένα αρχείο με δέκα μεγάλα κελιά θέλει δέκα προσπάθειες για να τα δείξει όλα.
**Τα πεδία** (σε παρένθεση το μήκος της στήλης):
*   **Πελάτης:** επώνυμο, όνομα, πατρώνυμο, Δ.Ο.Υ. (100 το καθένα), οδός (200), πόλη (100), email (255).
*   **Όχημα:** πινακίδα (10), μάρκα (50), μοντέλο (100), κατηγορία (10), χρώμα (50), αριθμός κινητήρα (50), Euro (20), οδός (200) και πόλη (100) της άδειας. Μάρκα, κατηγορία, χρώμα και Euro γίνονται λίστες στο Task 23, αλλά μια τιμή εκτός λίστας από την εισαγωγή μένει κείμενο όπως ήρθε, άρα ο έλεγχος χρειάζεται κι εκεί.
*   **Συμβόλαιο:** ασφαλιστική εταιρεία (100)· ο αριθμός συμβολαίου περνά στον κοινό έλεγχο.
*   **Διαμεσολαβητής**, μόνο από την εισαγωγή: ονοματεπώνυμο (200).
*   Οι σημειώσεις του πελάτη (`notes`, TEXT) δεν έχουν όριο στη βάση και μένουν έτσι.
**Ο κανόνας:**
*   **Ένα σημείο για τα όρια:** τα `@Column(length = …)` των entities, που υπάρχουν ήδη για κάθε στήλη, διαβάζονται από ένα βοηθητικό του `service`· το χρησιμοποιούν τα services των φορμών και η εισαγωγή (CLAUDE.md: το `importer` δεν ξαναγράφει κανόνες). Ένα test τα συγκρίνει με το `information_schema` της PostgreSQL, ώστε ένα migration που αλλάζει μια στήλη να μην αφήνει πίσω παλιό όριο.
*   **Μέτρηση σε χαρακτήρες**, όπως μετρά το `VARCHAR(n)` της PostgreSQL, όχι σε bytes: ένα επώνυμο 100 ελληνικών γραμμάτων χωρά. Η μέτρηση γίνεται σε code points, ώστε ένας χαρακτήρας έξω από το BMP να μετρά ένας, όπως στη βάση.
*   **Στη φόρμα:** μήνυμα δίπλα στο πεδίο, «Έως 100 χαρακτήρες (γράφτηκαν 104).», και η φόρμα κρατά ό,τι γράφτηκε, όπως με κάθε άλλο λάθος. Χωρίς `maxlength` στα πεδία: ο browser κόβει σιωπηλά ό,τι επικολλάται πέρα από το όριο, ενώ έτσι ο υπάλληλος βλέπει όλο το κείμενο και διαλέγει τι θα κρατήσει. Ο έλεγχος γίνεται στην τιμή όπως θα σωθεί, μετά από όποια αλλαγή κάνει το service (π.χ. η πινακίδα χωρίς παύλα, Task 14).
*   **Στην εισαγωγή:** κάθε κελί κειμένου ελέγχεται πριν γραφτεί η γραμμή, οπότε η αναφορά δείχνει **όλα** τα μεγάλα κελιά και των δύο αρχείων σε μία προσπάθεια: «Γραμμή 12, στήλη «Οδός (C.1.3)»: έως 200 χαρακτήρες (έχει 215)». Η εισαγωγή τότε δεν κρατά τίποτα, όπως με κάθε απορριφθείσα γραμμή· τα κελιά διορθώνονται στο Excel και η εισαγωγή ξανατρέχει. *   **Το `FormErrors` δεν αλλάζει:** μια παραβίαση της βάσης που δεν είναι unique index φτάνει ακόμη στη σελίδα σφάλματος, γιατί μετά από αυτό το task είναι bug.
