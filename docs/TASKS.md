# Σχέδιο Υλοποίησης (TASKS)

Το παρακάτω σχέδιο χωρίζει την υλοποίηση της εφαρμογής σε λογικά, διαδοχικά βήματα. Τα πιο επίφοβα (risky) κομμάτια, όπως η κανονικοποίηση κειμένου, το "έξυπνο" search και η εισαγωγή των Excel, τοποθετούνται πολύ νωρίς, ώστε τυχόν προβλήματα να εντοπιστούν πριν χτιστεί το UI και οι υπόλοιπες λειτουργίες πάνω τους.

Κάθε Task είναι σχεδιασμένο να υλοποιείται σε ένα session και να αφήνει την εφαρμογή λειτουργική, με τα tests της να περνούν επιτυχώς.

---

## Task 1: Project Skeleton & End-to-End Slice
**Στόχος:** Στήσιμο του περιβάλλοντος και δημιουργία του πρώτου λειτουργικού "end-to-end slice" της εφαρμογής (βάση, backend, api) με μόνο έναν πίνακα, ως απόδειξη ότι η υποδομή λειτουργεί.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `docker-compose.yml` (PostgreSQL)
*   `pom.xml` (Spring Boot Web, Data JPA, Flyway, PostgreSQL Driver, Testcontainers)
*   `application.yml` (DB connection, Flyway config)
*   `src/main/resources/db/migration/V1__init_customer.sql` (Δημιουργία πίνακα `customer` μόνο)
*   `Customer.java` (JPA Entity)
*   `CustomerRepository.java` (Spring Data Repo)
*   `CustomerController.java` (REST endpoint: `GET /api/customers`)
*   `CustomerControllerTest.java` (Integration test)
**Κριτήρια Αποδοχής:** Η εντολή `docker-compose up` ξεκινάει τη βάση. Το Spring Boot ξεκινάει χωρίς λάθη και τρέχει το Flyway migration. Μια κλήση στο `/api/customers` επιστρέφει JSON 200 OK. Το test περνάει επιτυχώς.

## Task 2: Search Normalization Foundation (High Risk)
**Στόχος:** Υλοποίηση της κανονικοποίησης κειμένου. Αυτό πρέπει να γίνει νωρίς, ώστε να υπάρχει ένα και μοναδικό σημείο αλήθειας (Single Source of Truth) τόσο για το Entity Lifecycle όσο και για το SearchService.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `V2__unaccent_wrapper.sql` (Extensions `unaccent`/`pg_trgm`, custom `IMMUTABLE` PostgreSQL συνάρτηση γύρω από την `unaccent`, στήλη `customer.search_normalized` ως `GENERATED ALWAYS AS (...) STORED` και GIN index πάνω της)
*   `TextNormalizationUtils.java` (Java utility class: αφαίρεση τόνων/κεφαλαία για το input αναζήτησης, κανονικοποίηση πινακίδας με αντιστοίχιση ελληνικών→λατινικών)
*   `TextNormalizationUtilsTest.java` (Unit tests)
*   `Customer.java` (Αντιστοίχιση του `search_normalized` ως read-only: `insertable = false, updatable = false`. **Όχι** `@PrePersist` για αυτό το πεδίο.)
*   `SearchNormalizationConsistencyTest.java` (Integration test με Testcontainers)
**Απόφαση:** Το `search_normalized` υπολογίζεται στη **βάση** (generated column), ώστε να γεμίζει και σε εγγραφές που παρακάμπτουν το JPA (import, χειροκίνητο SQL, migrations). Το `plate_normalized` μένει σε `@PrePersist`/`@PreUpdate` στο `Vehicle` (Task 3) μέσω του `TextNormalizationUtils`, γιατί η αντιστοίχιση ελληνικών→λατινικών είναι δύσχρηστη σε SQL.
**Κριτήρια Αποδοχής:** Το Flyway migration περνάει. Τα unit tests αποδεικνύουν ότι τα τονισμένα ελληνικά γίνονται άτονα, οι ελληνικοί χαρακτήρες πινακίδων (π.χ. 'Α', 'Β', 'Ε') γίνονται οι λατινικοί 'A', 'B', 'E', οι παύλες/κενά αφαιρούνται από τις πινακίδες και όλα μετατρέπονται σε κεφαλαία. Το `search_normalized` γεμίζει αυτόματα τόσο κατά την αποθήκευση Customer μέσω JPA όσο και με απευθείας `INSERT` σε SQL. Το consistency test επιβεβαιώνει ότι η Java κανονικοποίηση του input δίνει το ίδιο αποτέλεσμα με τη συνάρτηση της βάσης (τονισμένα, πεζά/κεφαλαία, τελικό σίγμα).

## Task 3: Πλήρες Σχήμα & MapStruct DTOs
**Στόχος:** Ολοκλήρωση του Data Model (χωρίς soft deletes) βάσει των προδιαγραφών και εισαγωγή των DTOs για την απομόνωση του domain model.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `V3__full_schema.sql` (Πίνακες `vehicle`, `policy`, `ownership`, `intermediary`, `app_user`, `audit_log` και GIN indexes)
*   Entities (`Vehicle.java`, `Policy.java` κλπ.)
*   Repositories για τα entities.
*   `pom.xml` (Προσθήκη MapStruct)
*   `*Dto.java` και `*Mapper.java` (MapStruct interfaces)
**Κριτήρια Αποδοχής:** Το Spring Data JPA ξεκινάει χωρίς errors για τις σχέσεις (OneToMany, ManyToMany). Το πεδίο `engine_cc` είναι nullable. Τα πεδία `tax_id` και `mobile` είναι nullable. Τα unique indexes υπάρχουν και δεν έχουν `WHERE deleted_at IS NULL`. Οι MapStruct mappers γίνονται generate στο compile-time επιτυχώς.

## Task 4: Excel Import Service (High Risk)
**Στόχος:** Ανάγνωση των παλιών Excel αρχείων και μεταφορά τους στη νέα βάση δεδομένων, ώστε να έχουμε ρεαλιστικά δεδομένα για το υπόλοιπο development.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `pom.xml` (Προσθήκη Apache POI)
*   `gr.insuranceoffice.importer.ExcelImporterService.java`
*   `ExcelImporterServiceTest.java`
**Κριτήρια Αποδοχής:** Η υπηρεσία διαβάζει ένα dummy Excel και το χαρτογραφεί στα entities. Μετατρέπει τα strings `«ΝΑΙ (Ν.Ο.Δ.)»` σε boolean. Αν το service τρέξει 2 φορές στο ίδιο αρχείο (idempotency), δεν δημιουργεί διπλότυπα αλλά κάνει update μέσω του natural key (`tax_id`, `vin`). Η εγγραφή "Αλεξίου Μαρία" σώζεται κανονικά παρόλο που λείπουν τα τηλέφωνα. 
**Σημείωση:** Ο importer είναι εργαλείο **εφάπαξ μετάπτωσης** από τα Excel, όχι λειτουργία καθημερινής χρήσης. Οι κίνδυνοι στο `docs/NOTES.md` («Import risks»: η επανεκτέλεση αντικαθιστά αλλαγές που έγιναν στην εφαρμογή, και αφαιρεί ιδιοκτησίες που λείπουν από το αρχείο) γίνονται πραγματικοί μόλις παραδοθούν τα Tasks 11a–11d, γιατί από εκεί και πέρα τα δεδομένα αλλάζουν μέσα από την εφαρμογή.

## Task 5: Έξυπνη Αναζήτηση (Smart Search)
**Στόχος:** Υλοποίηση της single search box λογικής με Type Detection μέσω Regex.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `SearchService.java`
*   `SearchServiceTest.java`
*   `SearchResultDto.java`
*   `SearchController.java`
**Κριτήρια Αποδοχής:** Το service δέχεται ένα input string. Αν κάνει match το VIN regex (`^[A-HJ-NPR-Z0-9]{17}$`), ψάχνει μόνο στο `VehicleRepository.findByVin()`. Αν είναι 9 ψηφία, στο ΑΦΜ. Αλλιώς, περνάει το input από το `TextNormalizationUtils`, εκτελεί fallback GIN query στους πίνακες `customer` και `vehicle`, συλλέγει τα αποτελέσματα και τα ομαδοποιεί. Τα tests επικυρώνουν σωστό routing του regex και απουσία N+1 queries.

**Αρχεία (δημιουργία/τροποποίηση):**

## Task 7: Optimistic Locking & Advanced Validation
**Στόχος:** Εφαρμογή των επιχειρησιακών κανόνων και του concurrency control.
**Αρχεία (δημιουργία/τροποποίηση):**
*   Προσθήκη `@Version` πεδίου `version` σε Πελάτη, Όχημα, Συμβόλαιο.
*   `CustomerService.java` (Business validations)
*   `GlobalExceptionHandler.java` (Controller Advice)
**Κριτήρια Αποδοχής:** Μια ταυτόχρονη αλλαγή ρίχνει `OptimisticLockException` και το API επιστρέφει HTTP 409 Conflict. Η αποθήκευση Πελάτη **χωρίς κινητό** περνάει, ΕΚΤΟΣ αν ο πελάτης είναι "Κύριος Ιδιοκτήτης" (is_primary = true) σε ενεργό όχημα με τρέχον συμβόλαιο, οπότε και το service ρίχνει Business Exception. Απουσία ΑΦΜ δεν ρίχνει λάθος αλλά μπορεί να επιστρέψει προειδοποίηση.

## Task 11: Φόρμες Καταχώρησης (Δημιουργία & Επεξεργασία)

Το αρχικό Task 11 ήταν τέσσερις φόρμες σε ένα session. Σπάει σε πέντε
διαδοχικά Tasks (11a–11e), καθένα από τα οποία ολοκληρώνεται σε ένα session
και αφήνει την εφαρμογή λειτουργική με πράσινα tests. Η σειρά έχει σημασία:
η ιδιοκτησία χρειάζεται πελάτη και όχημα, το συμβόλαιο χρειάζεται όχημα, και
οι ρόλοι φυλάνε τις ενέργειες που προσθέτουν τα προηγούμενα.

Κοινά για όλες τις φόρμες (11a–11d):
*   Οι controllers δουλεύουν **μόνο με DTOs** και καλούν services· η επικύρωση ζει στα services και δεν επαναλαμβάνεται σε controller ή JavaScript.
*   Κάθε σφάλμα εμφανίζεται μέσα στη φόρμα, δίπλα στο πεδίο που αφορά (ή στην κορυφή, αν αφορά όλη την εγγραφή), και οι τιμές που πληκτρολογήθηκαν δεν χάνονται.
*   Σύγκρουση optimistic locking (Task 7) εμφανίζει μήνυμα στη φόρμα και δεν αντικαθιστά σιωπηλά την αλλαγή του άλλου χρήστη· το `version` ταξιδεύει ως κρυφό πεδίο.
*   Οι φόρμες είναι POST με CSRF token (Task 10) και κάθε αποθήκευση καταγράφεται στο `audit_log` με τον συνδεδεμένο χρήστη (Tasks 6, 10).
*   Ελληνικές ετικέτες, τιμές enum όπως στο `DATA_MODEL.md`, ημερομηνίες `dd/MM/yyyy`, ποσά με ελληνική μορφή.

**Κριτήρια Αποδοχής:** Ο υπάλληλος δημιουργεί νέο πελάτη από την κεντρική πλοήγηση και επεξεργάζεται υπάρχοντα από την καρτέλα του Task 9. Ισχύει η επικύρωση του `CustomerService`: checksum ΑΦΜ (DATA_MODEL «Έλεγχος ΑΦΜ»), μορφή κινητού/σταθερού/Τ.Κ./email, υποχρεωτικό επώνυμο. ### Task 11c: Φόρμα Ιδιοκτησίας
**Στόχος:** Σύνδεση πελατών με όχημα και ποσοστά, με τον κανόνα του `OwnershipService` (Task 3/4) να επιβάλλεται από το UI.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `templates/ownership-form.html`
*   `OwnershipController.java`
*   `OwnershipService.java` (φόρτωση των τρεχόντων ιδιοκτητών ενός οχήματος και αποθήκευσή τους μαζί, σε ένα transaction)
*   Integration tests
**Κριτήρια Αποδοχής:** Η φόρμα επεξεργάζεται **μαζί όλους τους τρέχοντες ιδιοκτήτες** ενός οχήματος, αφού μία-μία γραμμή δεν μπορεί να περάσει τον έλεγχο. Ο υπάλληλος προσθέτει και αφαιρεί γραμμές, επιλέγει πελάτη με αναζήτηση (ΑΦΜ ή όνομα· αν δεν υπάρχει, δημιουργείται πρώτα με τη φόρμα του Task 11a) και ορίζει ποσοστά. Το άθροισμα των ποσοστών = 100 και ακριβώς ένας κύριος ιδιοκτήτης, αλλιώς η αποθήκευση απορρίπτεται με μήνυμα στην κορυφή της φόρμας. Δεν επιτρέπεται να γίνει κύριος ιδιοκτήτης οχήματος με τρέχον συμβόλαιο πελάτης χωρίς κινητό (DECISIONS §1, `docs/NOTES.md` «Mobile rule from the other side»).
**Απόφαση:** Όταν αφαιρείται ιδιοκτήτης, η γραμμή **κλείνει με `to_date`**, δεν διαγράφεται. Η μεταβίβαση είναι γεγονός με ημερομηνία, και η καρτέλα οχήματος (Task 9) ήδη δείχνει τους πρώην ιδιοκτήτες ξεθωριασμένους — η διαγραφή θα έκανε αυτή τη λειτουργία νεκρό κώδικα. Άρα η φόρμα δεν αφαιρεί ποτέ γραμμές από τη βάση και **δεν χρειάζεται `orphanRemoval`** στο `Vehicle.ownerships` (`docs/NOTES.md`, Finding 2).

### Task 11d: Φόρμα Συμβολαίου
**Στόχος:** Δημιουργία και επεξεργασία Συμβολαίου, με τους κανόνες του συμβολαίου στο `PolicyService`. Είναι η φόρμα που θα ξαναχρησιμοποιήσει το Task 12.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `templates/policy-form.html`
*   `PolicyController.java`
*   `PolicyService.java` (`create`/`update` + επικύρωση)
*   Integration tests
**Κριτήρια Αποδοχής:** Ο υπάλληλος δημιουργεί και επεξεργάζεται συμβόλαιο από την καρτέλα οχήματος. Επικύρωση στο `PolicyService`:
*   μοναδικός αριθμός συμβολαίου
*   λήξη > έναρξη
*   συμβόλαια του ίδιου οχήματος που δεν επικαλύπτονται χρονικά· **η κοινή ημέρα ορίου δεν είναι επικάλυψη** (βλ. Απόφαση παρακάτω)
*   ασφάλιστρο αριθμητικό με 2 δεκαδικά (όχι κείμενο «180,00 €»)· η ελληνική υποδιαστολή γίνεται δεκτή στην είσοδο
*   τύπος επασφαλίστρου μόνο όταν υπάρχει επασφάλιστρο, με τις τιμές `ΝΕΟΣ_ΟΔΗΓΟΣ` / `ΗΛΙΚΙΑΣ` / `ΑΛΛΟ`

*   Μενού χρήστη, εκεί που ήταν το όνομα: δείχνει το όνομα του συνδεδεμένου χρήστη, με «Αποσύνδεση» μέσα στο μενού (το ίδιο POST `/logout` form, τώρα μέσα σε ένα dropdown item).
*   Το search box μένει ένα ενιαίο ορατό πεδίο σε κάθε πλάτος, χωρίς αλλαγή συμπεριφοράς (SPEC §6, DECISIONS §3 — καμία επιλογή τύπου).
*   Τίποτα στο header δεν σπάει σε δεύτερη γραμμή σε καμία τυπική πλάτη· όλα τα στοιχεία κάθετα κεντραρισμένα. Σε στενά πλάτη (π.χ. ~375px) χρησιμοποιείται το τυπικό Bootstrap navbar-toggler/collapse (hamburger), ώστε τα στοιχεία να κρύβονται πίσω από ένα κουμπί αντί να σπάσουν.
*   Ελεγμένο οπτικά σε τουλάχιστον δύο πλάτη: desktop και στενό/mobile.

### Task 16c: Θέμα (light/dark)
**Στόχος:** Επιλογέας φωτεινού/σκοτεινού θέματος πάνω δεξιά, με το μηχανισμό `data-bs-theme` του Bootstrap 5.3 (ήδη εξάρτηση, `bootstrap.version` 5.3.8 στο `pom.xml`) — όχι custom CSS θέματος.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `templates/layout.html` (`data-bs-theme` στο `<html>`· ένα μικρό inline script **πριν** το CSS, ώστε το θέμα να εφαρμόζεται πριν αποδοθεί το πρώτο frame — όχι αναλαμπή λάθος θέματος)
*   `templates/fragments/header.html` (το κουμπί toggle, δίπλα στο μενού χρήστη του 16b)
*   `src/main/resources/static/js/theme.js` (νέο, τοπικό: ανάγνωση αποθηκευμένης επιλογής, αλλιώς `window.matchMedia('(prefers-color-scheme: dark)')`· εφαρμογή στο `data-bs-theme`· αποθήκευση της επιλογής του χρήστη όταν πατά το toggle)
**Κριτήρια Αποδοχής:**
*   Χωρίς προηγούμενη επιλογή του χρήστη, το θέμα ακολουθεί την προτίμηση του λειτουργικού/browser.
*   Το toggle αλλάζει αμέσως το θέμα σε όλη τη σελίδα και η επιλογή θυμάται σε επόμενη επίσκεψη ή αλλαγή σελίδας.
*   Καμία αναλαμπή λάθος θέματος κατά τη φόρτωση.
*   Ελεγμένο οπτικά και στα δύο θέματα, σε τουλάχιστον μια λίστα/καρτέλα και μια φόρμα — το κείμενο και τα στοιχεία παραμένουν ευανάγνωστα και στα δύο.

### Task 16d: Οπτική βελτίωση
**Στόχος:** Γενική βελτίωση εμφάνισης, χωρίς αλλαγή λειτουργίας, πάνω στο header του 16b και τις φόρμες του 16a.
**Αρχεία (δημιουργία/τροποποίηση):**
*   `templates/layout.html` ή νέο `src/main/resources/static/css/app.css` (κοινό CSS: πλαίσια/φόντο των inputs πριν το focus, hover/focus states, στιλ καρτών ενοτήτων)
*   `templates/customer-form.html`, `templates/vehicle-form.html`, `templates/policy-form.html`, `templates/ownership-form.html` (οι ενότητες της φόρμας —π.χ. «Ταυτότητα», «Τεχνικά», «Διεύθυνση άδειας» στο `vehicle-form.html`— μέσα σε `card`)
*   `templates/vehicle-detail.html` (τα κουμπιά ενεργειών ανά γραμμή στον πίνακα συμβολαίων —«Ανανέωση», «Επεξεργασία», «Διαγραφή», όχι πάντα και τα τρία μαζί— ίδιο μέγεθος μεταξύ γραμμών· το ίδιο στον πίνακα ιδιοκτητών· η στήλη «Από / Έως» του πίνακα ιδιοκτητών κρύβεται όταν είναι κενή σε κάθε γραμμή· `tel:` link στο κινητό κάθε ιδιοκτήτη)
*   `templates/customer-detail.html` (η στήλη «Από / Έως» του πίνακα συμβολαίων κρύβεται όταν είναι κενή σε κάθε γραμμή· `tel:` link στο κινητό του πελάτη)
*   `templates/dashboard.html` (`tel:` link στο κινητό κάθε γραμμής)
**Κριτήρια Αποδοχής:**
*   Κάθε input/select/textarea έχει ορατό περίγραμμα και ελαφρύ φόντο πριν πάρει focus (όχι μόνο κάτω γραμμή), σε φωτεινό και σκοτεινό θέμα (16c).
*   Κάθε κλικαρόμενο στοιχείο (κουμπιά, links, dropdown items) έχει ευδιάκριτο hover και focus state, με πληκτρολόγιο (tab) όχι μόνο με ποντίκι.
*   Οι ενότητες κάθε φόρμας εμφανίζονται μέσα σε ξεχωριστές κάρτες (`card`), όχι απλά `<h2>` πάνω από πεδία.
*   Τα κουμπιά ενεργειών σε κάθε γραμμή πίνακα έχουν το ίδιο ύψος/πλάτος μεταξύ γραμμών, ακόμα κι όταν μια γραμμή έχει λιγότερα κουμπιά από άλλη (π.χ. δεν εμφανίζεται «Ανανέωση» σε κάθε γραμμή).
*   Κάθε εμφανιζόμενο κινητό τηλέφωνο είναι σύνδεσμος `tel:`.
*   Η στήλη «Από / Έως» (πίνακας ιδιοκτητών στο `vehicle-detail.html`, πίνακας συμβολαίων στο `customer-detail.html`) κρύβεται εξ ολοκλήρου όταν καμία γραμμή της τρέχουσας σελίδας δεν έχει τιμή, ανά πίνακα.
*   Ελεγμένο οπτικά σε φωτεινό και σκοτεινό θέμα, σε τουλάχιστον μία φόρμα, μία καρτέλα (vehicle-detail ή customer-detail) και μία λίστα.
