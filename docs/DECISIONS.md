# Αποφάσεις και Αξιολόγηση Προδιαγραφών (DECISIONS)

Αυτό το έγγραφο καταγράφει σημεία των `SPEC.md` και `DATA_MODEL.md` όπου εντοπίζεται τεχνικό ρίσκο, αρχιτεκτονική πολυπλοκότητα ή προτείνεται διαφορετική προσέγγιση για τη διευκόλυνση της ανάπτυξης, ειδικά από έναν junior developer.

## 1. Το πεδίο `is_stub` στον Πελάτη

*   **Τι αναφέρει η προδιαγραφή:** Το πεδίο `mobile` είναι υποχρεωτικό, αλλά προτείνεται ένα πεδίο `is_stub BOOLEAN` για να "χαλαρώνει" τον έλεγχο σε περιπτώσεις συνιδιοκτητών που δεν έχουν κινητό, επιτρέποντας την εγγραφή τους.
*   **Το πρόβλημα:** Αν το `mobile` είναι `NOT NULL` στο επίπεδο της βάσης δεδομένων, η εφαρμογή δεν μπορεί να το "χαλαρώσει" χωρίς να βάλει κάποια "ψεύτικη" τιμή (π.χ. `0000000000`), κάτι που μολύνει τα δεδομένα. Αν γίνει `NULL` στη βάση, το `is_stub` προσθέτει περιττή πολυπλοκότητα (business logic, if-statements, UI toggles). Επίσης, τι συμβαίνει όταν ένας "stub" πελάτης αγοράσει δικό του συμβόλαιο; Πρέπει να υπάρχει μηχανισμός μετάβασης/αφαίρεσης του flag.
*   **Τι προτείνω αντί αυτού:** Καταργήστε εντελώς το `is_stub`. Κάντε το `mobile` nullable (`NULL` επιτρεπτό) στη βάση δεδομένων. Ο έλεγχος υποχρεωτικότητας του κινητού πρέπει να γίνεται **μόνο** όταν ο πελάτης συνδέεται ως "Κύριος Ιδιοκτήτης" (Primary) σε ένα ενεργό συμβόλαιο. Στο UI, ένας πελάτης χωρίς κινητό μπορεί απλά να έχει μια οπτική ένδειξη (π.χ. "Λείπουν στοιχεία επικοινωνίας"), χωρίς να δημιουργείται διαχωρισμός "κανονικών" και "stub" πελατών στο σχήμα.

## 2. Το ΑΦΜ (`tax_id`) ως φυσικό κλειδί (Natural Key)

*   **Τι αναφέρει η προδιαγραφή:** Το πεδίο `tax_id` είναι `NOT NULL` και `UNIQUE`. Αποτελεί το φυσικό κλειδί του πελάτη.
*   **Το πρόβλημα:** Η πραγματικότητα στην Ελλάδα είναι ότι ενδέχεται να υπάρξουν περιπτώσεις πελατών (π.χ. ανήλικοι συνιδιοκτήτες, αλλοδαποί χωρίς ελληνικό ΑΦΜ, ή απλώς βιαστική καταχώρηση στο γκισέ) όπου το ΑΦΜ δεν είναι άμεσα διαθέσιμο. Ένας αυστηρός περιορισμός `NOT NULL` σε επίπεδο βάσης θα μπλοκάρει τη ροή εργασίας (ο υπάλληλος δεν θα μπορεί να αποθηκεύσει τον πελάτη). 
*   **Τι προτείνω αντί αυτού:** Το `id` (BIGSERIAL) παραμένει το πρωτεύον κλειδί (Primary Key). Το `tax_id` πρέπει να γίνει `NULLABLE`. Ο περιορισμός `UNIQUE` παραμένει, αλλά με τον κανόνα της PostgreSQL όπου πολλαπλά `NULL` επιτρέπονται. Αν το σύστημα εντοπίσει ότι λείπει το ΑΦΜ, θα επιτρέπει την αποθήκευση αλλά θα προειδοποιεί τον χρήστη.

## 3. Ενιαίο Search Box με Type Detection

*   **Τι αναφέρει η προδιαγραφή:** Ένα και μοναδικό πεδίο αναζήτησης, όπου το σύστημα μαντεύει με Regex (Type Detection) αν ο χρήστης ψάχνει πινακίδα, ΑΦΜ, VIN, κινητό κ.λπ. 
*   **Το πρόβλημα:** Η μαντεψιά είναι εύθραυστη. Ένα string με 9 χαρακτήρες (π.χ. "ΑΛΕΞΙΟΥ99") μπορεί να μπερδέψει τους κανόνες. Επιπλέον, για την υλοποίηση απαιτείται να εκτελούνται πολλαπλά, ταυτόχρονα queries σε διαφορετικούς πίνακες (`customer`, `vehicle`), να συγκεντρώνονται τα δεδομένα στη Java, να ενοποιούνται σε ένα κοινό DTO και να σελιδοποιούνται (pagination). Για έναν junior developer, αυτό το "federated search" είναι πολύπλοκο και επιρρεπές σε καθυστερήσεις (N+1 query problems).
*   **Τι προτείνω αντί αυτού:** Εγκαταλείψτε το περίπλοκο Type Detection. Διατηρήστε μεν ένα κεντρικό Search Box, αλλά προσθέστε δίπλα ένα απλό dropdown (Επιλογή: "Πελάτης" / "Όχημα"). Ακόμα καλύτερα (και πιο εύκολο στην υλοποίηση) είναι να υπάρχουν δύο ξεχωριστά πεδία αναζήτησης (π.χ. ένα στην κορυφή της λίστας Πελατών και ένα στη λίστα Οχημάτων). Αυτό επιτρέπει στο Spring Data JPA να κάνει ένα απλό `Page<Customer> findBySearchNormalized(...)`, κρατώντας τον κώδικα καθαρό.
*   **ΑΠΟΦΑΣΗ (REJECTED):** Η πρόταση αυτή απορρίφθηκε. Το ενιαίο search box με type detection παραμένει. Η αιτιολόγηση είναι ότι ο χρήστης είναι υπάλληλος γραφείου με τον πελάτη να στέκεται μπροστά του· ένα type dropdown τον αναγκάζει να αποφασίσει τι είδους στοιχείο αναζητά πριν καν ξεκινήσει την πληκτρολόγηση. Η βέλτιστη εμπειρία χρήστη υπερτερεί της τεχνικής πολυπλοκότητας.

## 4. Χρήση Soft Deletes (`deleted_at`)

*   **Τι αναφέρει η προδιαγραφή:** Οι διαγραφές μαρκάρονται (soft delete) αντί να διαγράφονται οριστικά από τη βάση.
*   **Το πρόβλημα:** Το soft delete "μολύνει" όλη την εφαρμογή. Κάθε SQL ερώτημα που θα γράφετε (ή κάθε Spring Data Repository method) θα πρέπει να θυμάστε να περιλαμβάνει το `WHERE deleted_at IS NULL`. Οι `UNIQUE` περιορισμοί στη βάση σπάνε (εκτός αν χρησιμοποιήσετε partial indexes). Επειδή ήδη υλοποιείτε **Audit Logging** (που κρατάει παλιές/νέες τιμές σε JSONB), το soft delete είναι περιττή επικάλυψη που αυξάνει την τεχνική πολυπλοκότητα.
*   **Τι προτείνω αντί αυτού:** Χρησιμοποιήστε κανονικό Hard Delete (JPA `repository.delete()`). Αν κατά λάθος διαγραφεί μια εγγραφή, η πλήρης εικόνα της θα υπάρχει στον πίνακα `audit_log` (ο οποίος καταγράφει και τα `DELETE` actions με το παλιό JSON του αντικειμένου) και μπορεί να ανακτηθεί από εκεί από τον διαχειριστή.
